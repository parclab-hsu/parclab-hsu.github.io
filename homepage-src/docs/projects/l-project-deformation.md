# OmniLRS 지형 변형 엔진 정밀 분석

:material-circle:{ style="color:#2e9e44" } **기술 분석 노트** · 현대자동차 L-Project · 기준일 **2026-09-14** (최초 2026-09-10)

!!! abstract "요약"
    달 탐사 로버 HILS의 플랜트(NVIDIA Isaac Sim + OmniLRS)에는 바퀴자국을 만드는
    **지형 변형(Deformation/Sinkage) 엔진**이 들어 있습니다. 이 문서는 그 엔진을
    **우리 설정으로 재현해 계산하고, 실제로 켜서 측정한** 기록입니다.

    **지금 상태 (2026-09-14): 켜져 있고, 휠 근처를 1.5 cm 격자로 따로 그려 실제 휠 모양 —
    그라우저 24개의 무늬까지 — 이 이어진 자국으로 남습니다.** 거기까지 오면서 확인한 것은 이렇습니다.

    - **처음 설정으로 켜면 변형이 정확히 0이었습니다**(2절). 발자국 폭만 휠 폭으로 고치면
      **로버가 파묻혔고**(3절), 깊이가 하중이 아니라 **충격**에 비례해 하중 입력을 서스펜션
      조인트 토크로 바꿨습니다(4절).
    - **2026-09-11에 켰습니다.** 접지 길이·그라우저 주기·하중-깊이 회귀·안식각을 설계 침하
      0.020 m 한 세트로 맞추고, 스폰 충격이 새겨지지 않도록 시작 지연을 늘렸습니다(11절).
    - **켜고 주행하면 물리 시뮬레이션이 멈췄습니다.** 변형된 정점을 **충돌이 붙은 지형 메시**에
      그대로 써서, 물리 엔진이 256만 정점 충돌 메시를 다시 굽는 동안 물리 스텝을 건너뛰었습니다.
      렌더 전용 메시를 분리해 고쳤습니다 — 주행 중 RTF **0.008 → 0.22**, 멈춤 0(12절).
    - **발자국 폭을 휠 폭(0.159 m)으로 넣으면 0.10 m만 파였습니다.** 엔진이 양 끝 표본을 늘
      0으로 만들기 때문입니다. 0.21로 바꿔 실제 Isaac에서 **자국 폭 0.155~0.158 m(휠의
      97~100 %)** 가 됐습니다(13절).
    - **자국이 끊긴 점선 구덩이였습니다.** 칸 깊이가 처음 밟는 순간의 하중 하나로 정해지는데,
      주행 중 하중이 몇 배씩 출렁였습니다. 하중 저역통과와 최대 깊이 채택으로 자국을 따라간
      깊이 변동계수가 **0.74~0.88 → 0.27~0.37** 이 됐습니다(14절).
    - **깊이가 하중에 비례(선형)했습니다.** 강성륜 Bekker 식(n = 1)대로 **하중의 2/3제곱**으로
      바꿨습니다 — 하중이 두 배면 깊이는 1.59배입니다(15절).
    - **5 cm 격자로는 그라우저 무늬를 원리상 그릴 수 없었고, 지형 전체를 다시 쓰느라 주행 중
      RTF가 0.22였습니다.** 느린 원인은 정점 수가 아니라 쓰는 경로였습니다(64만 정점을 GPU 경로로
      매 반복 바꿔도 RTF 0.499). 휠 근처를 1 m 타일(1.5 cm)로 덮고 **휠 메시에서 잰 단면을 회전각에
      맞춰 찍게** 바꿨더니 주행 중 RTF **0.48~0.50**(변형을 끈 상태와 같음), 자국 깊이 24~27 mm ·
      그라우저 주기 55.8~56.4 mm(휠 기준 55.9) · 폭 0.164 m가 됐습니다(16절).

    **남은 것:** 토양 계수와 깊이는 시험 자료가 아니라 **목표값**(Bekker 21.6 mm · Lunokhod
    21~24 mm 범위)에 맞춘 것이고, 둔덕·벽 경사는 **추정**이며, 자국은 **보이기만 하고 밟히지는
    않습니다**(9절). 파라미터를 고치려면 **17절**, 처음에 왜 안 됐는지는 **18절**에 한눈에 정리했습니다.

## 1. 무엇을 하는 기능인가

로버 휠이 지나간 자리의 **DEM(높이맵)을 직접 깎습니다.** 깎인 높이는 **렌더 전용 메시**에만
반영됩니다 — 물리 충돌 메시는 그대로라, 자국은 **보이지만 로버가 밟지는 않습니다**(12절).

!!! info "2026-09-14부터 자국은 고해상도 타일이 만듭니다"
    아래 그림은 0.05 m 지형 격자를 직접 깎는 **원래 경로**입니다. 지금은 휠 근처만 1.5 cm 타일로
    따로 그리고 실제 휠 단면을 찍는 경로(16절)가 자국을 만들며, 이 그림의 발자국·분포·회귀 계수는
    그 경로를 끌 때만 쓰입니다(17절). 두 경로 모두 **물리 충돌 메시는 바꾸지 않습니다.**

!!! note "정정 (2026-09-11 · 2026-09-14)"
    이 절에는 원래 "PhysX 콜라이더가 그 DEM에서 다시 생성되므로 파인 자국이 이후 주행에
    영향을 준다"고 적혀 있었습니다. 소스를 따라가 보니 틀렸습니다. 그리고 그 뒤에 적은
    "콜라이더는 그대로다"도 반만 맞았습니다 — 정점을 쓰던 메시가 **충돌이 붙은 바로 그
    메시**여서, 실제로는 충돌 메시가 계속 다시 구워지며 시뮬레이션을 멈추고 있었습니다(12절).
    지금은 렌더 메시와 충돌 메시를 분리해 **설계상** 충돌 메시가 바뀌지 않습니다.

``` mermaid
flowchart LR
    A["휠 링크 4개<br/>월드 포즈"] --> C["발자국 격자를<br/>월드 좌표로 투영"]
    B["하중<br/>(서스펜션 토크,<br/>0.3 s 저역통과)"] --> D["하중 → 침하 깊이<br/>회귀"]
    C --> E["DEM[y, x] =<br/>가장 깊은 값"]
    D --> E
    E --> F["렌더 전용 메시 갱신<br/>(바뀐 경우만)"]
    E -.->|"충돌 메시는 그대로"| G["PhysX 지형 충돌"]
```

참조점은 **휠 링크의 월드 원점(x, y)** 이고 방향은 **쿼터니언 yaw 하나**입니다.
따라서 조향은 반영되지만 **z·roll·pitch는 버려집니다** — 경사면에서 발자국이
지형에 눕지 않고 수평 격자로 찍힌다는 뜻입니다.

## 2. 현행 설정으로는 변형이 정확히 0 이다

가장 중요한 결과입니다. 현행 설정으로 `enable: True` 로 바꾸면 **아무 일도 일어나지
않고, 오류도 나지 않습니다.**

!!! warning "실동작으로 확인 (기준일 2026-08-25)"
    오프라인 계산이 아니라 실제로 켜서 확인했습니다. **12.156 m를 새 지형 위로 달려도
    격자가 한 칸도 바뀌지 않았습니다.** 접지력은 최대 **907 N** 으로 충분히 들어오는데도
    깊이가 0입니다 — 막히는 곳이 접지력도 좌표도 아니고 **경계 분포**임이 확정됐습니다.

### 원인 — 발자국 폭이 격자 두 칸보다 좁다

```
지형 해상도    0.05 m/px
발자국 폭      0.09 m   →  int(0.09/0.05)+1 = 2 점
발자국 길이    0.20 m   →  int(0.20/0.05)+1 = 5 점
```

경계 분포(안식각) 함수는 **가장자리에서 정확히 0**, 안쪽에서 −1입니다. 그런데 폭에
2점만 잡히면 그 둘이 **모두 가장자리**(`y = −1`, `+1`)가 되어 `boundary = [0, 0]` 이고,
최종 깊이가 `boundary × (…)` 이므로 **전부 0** 입니다.

| 발자국 폭 | 격자 점수 | 경계 분포 | 결과 |
|---|---|---|---|
| **0.090 m (현행)** | 2 | `[0, 0]` | **변형 없음** |
| 0.100 m | 3 | `[0, −1, 0]` | 발생 |
| **0.159 m (실제 휠 폭)** | 4 | `[0, −1, −1, 0]` | 발생 |
| 0.200 m | 5 | `[0, −0.87, −1, −0.87, 0]` | 발생 |

폭이 `2 × 지형해상도`(= 0.10 m)보다 작으면 **무조건 0** 입니다.

우리 휠 폭은 자산 실측 **0.159 m** 이고, 설정의 0.09는 그 **57 %** 입니다.
OmniLRS 예제값으로 보이며 근거가 문서 어디에도 없습니다.

!!! note "안식각을 낮춰서 풀 수 있는 문제가 아닙니다"
    폭이 2점이면 두 표본점이 모두 가장자리이고 거기서 식이 정확히 0이므로,
    **안식각 값과 무관하게 항상 0** 입니다. 폭을 늘려 점수를 3 이상으로 만드는 것
    외에 방법이 없습니다.

## 3. 폭을 고치면 이번엔 로버가 파묻힌다

`width: 0.159` 로 바꾸면 변형은 발생합니다. 그런데 깊이가 문제입니다.

| 하중 | 접촉력 | DEM 변화 | 휠 반경(0.2133 m) 대비 |
|---|---|---|---|
| 무하중 | 0 N | −0.0053 m | 2 % |
| **정상** | **182 N** (450 kg ÷ 4, 달 중력) | **−0.0946 m** | **44 %** |
| 2배 | 365 N | −0.1839 m | 86 % |

**정상 주행에서 휠 반경의 44 % 가 파입니다.** 실측에서는 같은 지령·같은 시간에
**12.156 m 대 0.054 m** 였습니다 — 로버가 제자리에서 자기 구덩이를 파고 갇힙니다.

그리고 **무하중에서도 5.3 mm가 파입니다.** 회귀식의 절편이 0이 아니기 때문입니다.

```
amplitude = 0.00006·F + 0.008     ← F = 0 에서 0.008
mean      = −0.00046·F − 0.0013   ← F = 0 에서 −0.0013
```

접촉력이 없어도 깊이가 나온다는 것은, **회귀가 맞춰진 구간 밖에서 물리적으로 말이
안 되는 값을 낸다**는 신호입니다. 그리고 이 네 계수가 **어떤 흙·어떤 휠·어떤 중력에서
맞춰진 것인지** 상류 문서에도 우리 설정에도 없습니다.

## 4. 하중 입력을 바꿨다 — 접지력은 정지 시 0으로 읽힌다

실측 과정에서 더 근본적인 문제가 드러났습니다. **PhysX 접지력이 정지·안착 상태에서
4륜 모두 0으로 읽힙니다**(1,680회 연속 확인). 움직이거나 충격이 있을 때만 수백 N이
나옵니다.

!!! danger "진짜 바퀴자국은 무거울수록 깊어야 하는데, 이 모델은 충격이 클수록 깊었습니다"
    서 있으면 안 파이고 부딪히면 파입니다. **발자국 폭을 고쳐도 남는 문제**입니다.

### 서스펜션 조인트 토크로 하중을 만든다 (기준일 2026-09-09)

서스펜션 조인트 토크는 **정지 상태에서도 살아 있고 지령에 반응합니다.** 조인트 축이
차량 종축(x)이므로, 수직력이 만드는 토크는 접지점까지의 **y 오프셋**에만 걸립니다.

```
F = (0, 0, −N),  r = 접지점 − 조인트 원점
(r × F)_x = −N · r_y      →      N = |τ| / |Δy|
```

레버 암은 하드코딩하지 않고 **URDF 체인에서 회전까지 합성해 계산**합니다. 중간에
0.1745 rad 회전이 있어 좌표를 단순히 더하면 5.7 mm 어긋나는데, 회전을 넣으면 휠 y가
**0.6433 m** 로 계약 윤거의 절반 **0.64335 m** 와 맞습니다 — 이것이 자기 검산이 됩니다.
레버 암 **0.4908 m**.

| 확인 항목 | 접지력 (전) | 서스펜션 토크 (후) |
|---|---|---|
| 정지 상태 하중 | 0 N | **148.85 N** |
| 값이 있는 휠 수 | 0 / 4 | **4 / 4** |
| 폭 0.159에서 침하 | — | 0.0906 m |
| DEM 변화 격자 | 0 칸 | **40 칸** |
| 그때 로버 이동 거리 | — | **0.0 m** |

**로버가 서 있는데 파입니다.** 이것이 이 연결의 목표였습니다.

### 다만 자중의 절반만 읽힙니다 — 결함이 아니라 기구입니다

야드 다섯 자리에서 재면 네 휠 하중의 합이 자중(729 N)의 **51.6 ~ 66.1 %**, 평균
**56.2 %** 입니다. 원인은 서스펜션이 **4절 평행링크**라는 데 있습니다 — 아래 팔이
**2력 부재**라 큰 힘을 나르면서도 자기 축 토크는 0입니다(실측 0.004 N·m).
**위 팔 토크만으로는 원리적으로 전체 하중을 볼 수 없습니다.**

따라서 고칠 문제가 아니라 **계수로 보정할 문제**이고, 교정 계수는 **1.78**,
**산포 ±18 %** 입니다. 평균은 맞고 자세별 오차는 남습니다.

## 5. 접지면(Footprint) 정밀 실측 — 폭 하나로 이야기할 문제가 아니었다

여기까지는 "휠 폭 0.159 m"라는 값 하나로 이야기했습니다. 휠 메시에서 직접 재 보니
**접지 폭은 하나가 아니고, 접지 길이는 상수가 아닙니다.** (기준일 2026-09-10)

접지 길이는 강체 휠 기하로 계산합니다 — 진입각 `θ_f = arccos(1 − z/R)` 의 현 길이이고,
이탈각을 진입각과 같다고 본 값입니다.

```
L = 2·√(2Rz − z²)          R = 0.2134 m (팁 반경 실측)
```

| 침하 z [m] | 걸리는 폭 [m] | 접지 길이 L [m] | 폭 격자점 | 길이 격자점 | `wave_frequency` |
|---|---|---|---|---|---|
| 0.0020 | **0.1297** | 0.0583 | 3 | 2 | 1.04 |
| 0.0050 | 0.1575 | 0.0918 | 4 | 2 | 1.64 |
| 0.0100 | 0.1589 | 0.1291 | 4 | 3 | 2.31 |
| 0.0200 | 0.1592 | 0.1804 | 4 | 4 | 3.23 |
| **0.0320** | 0.1592 | **0.2248** | 4 | 5 | 4.02 |
| **0.0500** | 0.1592 | **0.2745** | 4 | 6 | 4.91 |
| 0.0906 | 0.1592 | 0.3490 | 4 | 7 | 6.25 |

굵게 표시한 두 줄이 이 프로젝트의 실측 침하 범위입니다.

### 휠 폭은 상수로 둬도 됩니다 — 값은 0.159가 맞습니다

**그라우저 팁대(반경 99~100 %)의 폭은 0.1297 m** 로 전체 폭보다 **18 % 좁습니다.**
그런데 침하가 **5 mm만 넘으면 0.1575 → 0.1592로 포화**합니다. 실제 침하 범위에서는
항상 전체 폭이 걸리므로 **휠 폭을 상수 0.159로 보는 것은 타당합니다** — 팁대가 좁은 것은
첫 2 mm에서만 유효합니다.

!!! warning "정정 (2026-09-14) — 휠 폭을 발자국 폭 설정에 그대로 넣으면 안 됩니다"
    휠 폭 값 자체는 맞지만, 엔진은 발자국의 **양 끝 표본을 늘 깊이 0으로** 만듭니다.
    `footprint.width` 에 0.159를 넣으면 가운데 2칸 = **0.10 m(휠의 63 %)** 만 파입니다.
    지금은 0.21로 두어 0.150 m가 파이도록 했습니다(13절).

축방향 중심이 **−0.0031 m** 로 완전 대칭이 아닌 것도 확인했습니다. 발자국이 휠
중심선 기준으로 생성되므로 3 mm만큼 한쪽으로 치우칩니다 — 격자 0.05 m 대비 6 %라
지금은 무시할 수 있지만, 해상도를 올리면 보이게 됩니다.

### 길이는 상수로 두면 안 되고, 엔진이 갱신하지도 않습니다

!!! danger "접지면은 초기화 때 한 번만 만들어집니다"
    발자국 생성 함수가 엔진 `__init__` 에서 한 번만 호출됩니다. **침하가 깊어져도
    접지면이 넓어지지 않습니다.** 접지 면적이 고정된 채 하중만 늘면
    **압력이 과대평가되는 방향**입니다.

현행 설정 0.200 m는 **침하 0.0249 m에 해당하는 길이**입니다. 실측 침하 범위
0.032~0.05 m에서는 0.225~0.275 m여야 하므로 **12~37 % 과소**입니다.

### 설정 두 값이 서로 어긋나 있습니다

| 설정 항목 | 값 | 그 값이 가정하는 침하 | 그때의 접지 길이 |
|---|---|---|---|
| `footprint.height` | 0.200 | 0.0249 m | 0.200 m |
| `wave_frequency` | 4.14 | **0.0339 m** | **0.231 m** |

같은 접지면을 두 곳에서 다르게 가정하고 있습니다 — 길이 기준 **15.6 % 차이**입니다.
`wave_frequency` 를 3.58(길이 0.200 기준)로 맞추면 최소한 서로 모순이지는 않게 되지만,
그건 **일관성을 맞추는 것이지 옳게 만드는 것이 아닙니다.** 옳게 하려면 길이가 침하를
따라가야 합니다.

### 실제 접지면과의 유사도는 지금 46~56 % 입니다

"폭·길이가 맞는가"로는 부족합니다. **DEM에 실제로 찍히는 면적**으로 봐야 합니다 —
엔진은 발자국 표본점을 `int(좌표/해상도)` 로 격자 셀에 매핑하므로, 설정값이 아니라
**이산화된 결과**가 지형을 깎습니다.

발자국 생성이 `linspace(−w/2, w/2, int(w/res)+1)` 이라 **표본 간격이 지형 해상도와
다릅니다**(폭 0.159 → 4점, 간격 0.053). 그래서 셀이 겹치거나 건너뛰고,
**덮는 면적이 설정값보다 부풀어 오릅니다.**

| 설정 (폭 × 길이) | 표본점 | 찍힌 셀 | 덮는 폭 | 덮는 길이 | 찍힌 면적 |
|---|---|---|---|---|---|
| **0.090 × 0.200 (현행)** | 10 | 8.0 | **0.141** | 0.200 | 0.0200 m² |
| 0.159 × 0.200 | 20 | 16.0 | 0.210 | 0.200 | 0.0400 m² |
| 0.159 × 0.275 | 24 | 20.8 | 0.210 | 0.274 | 0.0519 m² |

셀 위상에 따라 달라지므로 무작위 위상 300~400회 평균입니다.
**현행 폭 0.090이 실제로는 0.141 m를 덮습니다 — 설정값의 1.57배입니다.**

실제 접지 면적은 침하 0.032 m에서 **0.0358 m²**, 0.050 m에서 **0.0437 m²** 입니다.

| 조건 | 면적 유사도 (z=0.032) | (z=0.050) |
|---|---|---|
| **현행 0.090 × 0.200** | **56 %** | **46 %** |
| 폭·길이를 실제값으로, 해상도 0.05 | 114 % | 119 % |
| 폭·길이를 실제값으로, **해상도 0.025** | **99 %** | **101 %** |
| 〃 해상도 0.02 | 99 % | 96 % |

**90 % 이상을 만들려면 지형 해상도를 0.025 m/px로 올려야 합니다.** 현행 0.05에서는
폭·길이를 정확히 넣어도 이산화가 **14~19 % 과대**로 만듭니다 — 휠 폭 0.159가 격자
3.2칸이라 양자화 오차가 원리적으로 ±0.5칸(±15 %)이기 때문입니다.

!!! warning "정정 (2026-09-14) — 위 두 표는 깊이가 0인 표본까지 셌습니다"
    "찍힌 셀·덮는 폭"은 발자국 표본이 떨어지는 셀을 모두 센 값입니다. 그런데 엔진의 경계
    분포는 **양 끝 표본의 깊이를 늘 0으로** 만들어, 그 셀은 실제로는 파이지 않습니다.
    실제 엔진으로 자국을 찍어 재면 폭 0.159는 **2칸 = 0.10 m** 만 파였습니다 —
    「14~19 % 과대」가 아니라 **37 % 과소**였습니다. 파이는 칸 수는 「횡 표본 수 − 2」이고,
    발자국 폭 0.21에서 3칸 = 0.150 m가 됩니다(13절).

### 그런데 그 해상도에서 변형을 켜면 시뮬레이션이 멈춥니다

해상도만 올리는 것은 **런타임 비용이 없습니다** — tick 29.959 Hz, RTF 0.4994로
현행과 같습니다(기동만 40 s → 118 s로 늘어납니다).

| 조건 | tick | RTF |
|---|---|---|
| 0.05 · 변형 OFF | 29.96 Hz | 0.4994 |
| 0.05 · 변형 ON | 27.88 Hz | 0.4725 |
| 0.025 · 변형 OFF | 29.96 Hz | 0.4994 |
| **0.025 · 변형 ON** | **5.61 Hz** | **0.0000** |

!!! danger "RTF 0은 반올림이 아닙니다 — simulation time이 3.8 s에서 그대로 멈춥니다"
    그런데 관절 상태 토픽은 5.6 Hz로 계속 나옵니다(20초간 115건 수신, 스탬프는
    전부 3.8000). **밖에서 보면 살아 있는 것처럼 보입니다.**

원인은 변형 함수가 **깊이가 0이든 아니든 매 스텝 정점 배열 전체를 다시 쓰는**
구조입니다. 배열이 2.6 M → 10.2 M으로 4배가 되면서 한 스텝을 못 끝냅니다.

**즉 유사도 90 %는 지금 구현으로는 도달할 수 없습니다.** 해상도를 올리는 것이
조건인데 그 해상도에서 엔진이 서기 때문입니다. **바뀐 셀만 갱신하도록 고치는 것이
선행 조건**입니다.

### 그래서 지금 적용되어 있는가

**2026-09-10 기준으로는 아니었습니다** — 설정이 폭 0.090 · 길이 0.200이라 변형이 정확히 0인
상태였습니다. **2026-09-11에 켰고**(11절), 2026-09-14 현재 설정은 **폭 0.21 · 길이 0.1804** 입니다.
지형 해상도는 여전히 0.05 m/px입니다. **해상도를 올리는 대신 휠 근처만 1.5 cm 타일로 따로 그리는
방식으로 풀었습니다(16절)** — 실측 자국 폭 0.164 m(휠 0.159 m의 103 %).

## 6. 실행 파라미터 전수 점검 — 근거 있는 값은 3개뿐

**값이 적혀 있다고 쓰이는 것은 아닙니다.** 설정에 자리가 있는데 코드가 한 번도 읽지
않는 항목이 있고, 설정과 대상이 연결되지 않은 항목도 있습니다. 둘 다 겉으로는 정상으로
보입니다. (기준일 2026-09-08, 13개 항목 전수)

| 항목 | 상태 | 영향 |
|---|---|---|
| **`gravity`** | 설정에 있으나 엔진 소스에서 **참조 0회** | 값을 고쳐도 아무 일이 없다 |
| **`footprint.shape`** | 분기 자체가 없음 | **접지면이 항상 직사각형**이다 |
| **`num_links`** | `target_links` 로부터 채워지지 않음 | 기본값 4로 돌고, 휠이 4개라 **우연히 맞다** |
| **`angle_of_repose`** | 현행 60°, 출처 없음 | 폭을 고친 뒤 **깊이를 2.6배까지 좌우** |
| **`wave_frequency`** | 현행 4.14 = 접지 길이 0.20 m 기준 한 바퀴 27.8개분 | 실측은 **24개** |

### 그라우저는 24개다 (기준일 2026-08-26)

휠 메시에서 실측했습니다 — 방위각 히스토그램의 이산 푸리에 변환으로 지배 주파수를
보는 방식이며, 반경 문턱 98/95/92 %에서 모두 같은 답이 나왔습니다.

| 항목 | 실측 |
|---|---|
| **그라우저 수** | **24 개** |
| 휠 반경(팁) / 지름 | 0.2134 / 0.4268 m |
| **그라우저 높이** | 약 **19.1 mm** |

설정 주석은 `num_grouser/pi` 라고 적혀 있는데, **그 식은 접지 길이 L이 휠 지름과 같을
때만 성립합니다.** OmniLRS 기본값(반경 0.09, 길이 0.18)은 정확히 `L = 2R` 이라 맞았지만
우리는 아닙니다. 일반식 `L·N / (2πR)` 로 계산하면 현재 접지 길이 0.20 m에서 **3.58** 이고,
그 접지 길이 자체도 아직 근거가 없습니다.

## 8. 함께 확인한 것 — 견인 솔버는 한 번도 돌아본 적이 없었다

변형 엔진과 짝을 이루는 **Terramechanics 견인 솔버**도 같이 점검했습니다. 이 둘은
"지형의 모양을 바꾸는 쪽"과 "로버가 받는 힘을 바꾸는 쪽"으로 나뉘는데, 연결이
끊겨 있었습니다. (기준일 2026-09-10)

| | 결함 | 왜 드러나지 않았나 |
|---|---|---|
| ① | 호출부가 주석 처리 | 로버가 토양 반력을 안 받아도 화면은 정상 |
| ② | 기본 인자 **20 kg · 휠 반경 0.09 m** (실제 450 kg · 0.2133 m) | 값이 그럴듯했다 |
| ③ | 힘을 **2회 연속** 적용 | 두 줄이 나란히 있어 눈에 띄지 않는다 |
| ④ | 없는 API 호출(`get_velocities`) | 유일한 호출자가 주석이라 |
| ⑤ | 휠당 스칼라 자리에 (n,3) 월드 벡터 | 〃 |
| ⑥ | 수치적분 결과를 **튜플째** 연산 | 힘 계산 세 함수가 **한 번도 실행된 적 없음** |
| ⑦ | 중력 **9.81 하드코딩** | 달 시뮬레이터에서 σ_max가 **6배** 부푼다 |

일곱 건을 고쳐 연결한 뒤 실측하면 침하 0.032~0.05 m, 슬립비 0.846 → −0.189,
견인력 −48 ~ +4 N 범위에서 **NaN 없이 안정적으로** 돕니다.

!!! warning "다만 수직 반력은 더하지 않습니다"
    PhysX가 접촉으로 이미 지지력을 줍니다. 거기에 솔버의 수직 반력을 얹으면
    **이중 계상**이고, 출처 없는 계수로는 그것만으로 로버가 날아갑니다
    (σ_max 약 44 kPa → 휠당 1.5 kN 급, 자중은 729 N). 이 솔버로 보려는 것은
    **견인력과 저항 토크**입니다.

## 9. 확인되지 않은 것

이 절을 줄이지 않습니다. 위의 수치가 어디까지를 말하는지가 여기에 있습니다.

- **토양 계수의 출처가 없습니다.** 깊이는 시험 자료가 아니라 **목표값**에 맞췄습니다 — 정지
  하중 182 N에서 약 20 mm(Bekker 21.6 mm · Lunokhod 21~24 mm 범위), 그 밖에서는 하중^(2/3).
  Bekker/Wong 계수 9개도 출처가 없습니다. **월면토 시험 자료 없이는 크기를 믿을 수 없습니다** —
  확인한 것은 경향과 연결 여부입니다.
- **실제 월면토로 검증한 것이 아닙니다.** 전부 시뮬레이션 내부 계측이며,
  시뮬런트(모사토) 시험도 아직 없습니다.
- **하중 추정의 산포가 ±18 %** 입니다(교정 계수 1.78). 이것이 자국을 따라가는 깊이 출렁임으로
  남습니다 — 변동계수 0.25~0.30(16절).
- **둔덕·벽 경사는 추정입니다.** 옆으로 밀려난 흙의 비율(10 %)과 벽 임계각(60°)에는 정량
  문헌이 없고, 그라우저 자국 진폭(9~10 mm)은 단륜 시험의 6.09 mm보다 큽니다. 0.3 s보다 짧은
  충격은 자국에 남지 않습니다.
- **자국은 보이기만 하고 밟히지 않습니다**(12·16절). 반복 통과로 깊어지는 거동이나 슬립–침하
  연성은 충돌 메시가 갱신돼야 의미가 있습니다.
- **휠과 자국 바닥 사이가 몇 mm 어긋날 수 있습니다.** 자국은 렌더 지형을 기준으로 찍지만 휠은
  근사된 충돌 메시 위에 서 있어, 휠 팁과 지형 사이가 직진 중 평균 6 mm · p95 15 mm 차이 납니다(16절).
- **경사면 처리를 확인하지 않았습니다.** 자국은 휠의 수평 방향(진행·차축)만 써서 수직으로
  찍으므로 경사에서 오차가 생기는데, 그 크기를 재지 않았습니다.
- **제자리 선회·큰 슬립 자국의 사실감은 보지 않았습니다.** 직진과 완만한 선회 구간만 쟀습니다.
- **긴 주행에서 타일이 쌓입니다.** 185만 정점까지는 RTF 0.481로 쟀고, 1 km 주행(약 600만 정점)은
  재지 않았습니다.
- *(0.05 m 경로에만 해당)* 자국 중심이 휠보다 안쪽으로 약 1.5 cm 치우쳤던 것(13절)과 접지면 면적
  유사도 재계산(5절)은 확인하지 못한 채 남았습니다 — 지금 자국은 16절 경로가 만듭니다.

## 12. 켜고 주행하면 물리가 멈췄다 — 충돌 메시 재쿠킹 (기준일 2026-09-14)

**증상.** 로버에 주행 지령을 줘도 가지 않았습니다. 관절 상태 토픽은 24 Hz로 계속 나오는데
**헤더 스탬프만 반복**됐습니다. 정지해 있으면 멀쩡했고, 주행을 멈춰도 한동안 풀리지 않았습니다.

### 변형 엔진이 원인이다 — 켜고 끄기 대조

보드는 EPOS 백엔드로 내리고, 구동 4축 2.0 rad/s를 직접 주입했습니다. RTF는 스탬프 차 ÷ 벽시계, 5 s 창입니다.

| | 정지 | 주행 45 s | 멈춘 뒤 |
|---|---|---|---|
| 변형 ON | 0.424 | **0.008 · 멈춘 창 8/9 · 이동 0.08 m** | **0.003 · 9/9** |
| 변형 OFF | 0.497 | **0.497 · 0/9 · 이동 5.86 m** | 0.497 |

### 무엇이 멈추게 하나 — 한 컨테이너 안에서 쓰는 곳만 바꿔 봄

| 모드 | 하는 일 | 주행 중 |
|---|---|---|
| 정점 쓰기 생략 | 변형 계산만 | **RTF 0.499, 안 멈춤** |
| 충돌 없는 별도 메시에 쓰기 | 렌더만 갱신 | **안 멈춤** (RTF 0.23) |
| 암석 배치 갱신 생략 | 원래 메시에 씀 | **멈춤** |
| 원래 | 원래 메시에 씀 | **멈춤** |

**바뀐 정점이 충돌이 붙은 메시에 쓰일 때만 멈춥니다.** 멈춘 동안에도 시뮬레이션 루프는 돌고
(5 s에 약 125회, 한 번 8.5 ms) **물리 스텝 이벤트만 0** 이었습니다 — 느려진 게 아니라 건너뛴 것입니다.
물리 엔진의 쿠킹 결과가 쌓이는 캐시가 **충돌 메시에 쓸 때만 약 65 s마다 2 GiB씩** 찼고,
사흘 정지해 있는 동안에는 전혀 늘지 않았습니다.

!!! danger "수신 주기로 재면 정상으로 보입니다"
    토픽은 계속 나오기 때문에 수신 Hz만 보면 멀쩡합니다. 멈춤은 **스탬프가 바뀌는지**로 봐야 합니다.

### 고친 것과 확인

지형을 만들 때 **렌더 전용 메시**(충돌 없음)를 따로 두고, 변형은 거기에만 씁니다. 충돌 메시는
숨깁니다(숨겨도 충돌은 유지됩니다). 정점이 바뀌지 않으면 아예 쓰지 않습니다.

| | 고치기 전 | **고친 뒤** | 변형 OFF |
|---|---|---|---|
| 정지 RTF | 0.424 | **0.478** | 0.497 |
| 주행 RTF · 멈춘 창 · 45 s 이동 | 0.008 · 8/9 · 0.08 m | **0.222 · 0/9 · 4.26 m** | 0.497 · 0/9 · 5.86 m |
| 정지 30 s 동안 정점 쓰기 | 매 반복 | **0회** | — |
| 쿠킹 캐시 증가 | 약 65 s에 2 GiB | **0** | — |

주행 중 RTF가 0.22로 남은 것은 256만 정점 렌더 메시를 매번 다시 쓰는 비용이었고, 휠 근처만
Fabric으로 갱신하는 16절 방식으로 **0.48~0.50**까지 풀었습니다.

## 13. 발자국 폭은 휠 폭이 아니었다 — 0.159 → 0.21 (기준일 2026-09-14)

**자산 USD는 설정과 맞았습니다.** 시뮬레이션이 여는 로버 USD를 직접 쟀습니다.

| 항목 | 실측 (4륜 같음) |
|---|---|
| 휠 폭 · 반경 | 0.1592 m · 0.2134 m |
| 휠 링크 원점 | 휠 중심 — 가로로 3.1 mm만 어긋남 |
| 정지 자세 | 곧게 섬 (조인트의 ±10°는 조향축 킹핀 경사를 되돌리는 값) |
| 지형 메시 | 원점 · 무회전 · 배율 1 — 월드→격자 변환이 엔진과 맞음 |

**틀린 것은 매핑이었습니다.** 엔진의 경계 분포 `mask·(tan|y| − tan + 1) − 1` 은 발자국 가장자리
(|y| = 1)에서 **안식각과 무관하게 0** 입니다. 그래서 **양 끝 횡 표본은 늘 파지 않고**, 파이는 칸은
「횡 표본 수 − 2」가 됩니다. 실제 엔진으로 직진 자국을 찍어 바퀴와 격자의 위상을 10단계로 바꿔 쟀습니다.

| `footprint.width` | 횡 표본 | 파인 폭 | 휠 대비 |
|---|---|---|---|
| 0.159 (휠 폭) | 4 | **2칸 = 0.100 m** | **63 %** |
| **0.21 (지금)** | 5 | **3칸 = 0.150 m** | **94 %** |
| 0.265 | 6 | 4칸 = 0.200 m | 126 % |

폭을 바꾸면 경계 분포의 최댓값이 −0.667 → −1.0이 되어 같은 계수로는 깊이가 1.5배가 됩니다.
회귀 기울기 두 개를 ×2/3로 줄여 정상 하중 깊이 0.020 m를 유지했습니다.

**실제 Isaac에서 확인** — 3.9 m 직진 뒤 지형 데이터를 덤프해 쟀습니다.

| 줄 | 평균 파인 폭 | 휠 대비 | 중심 − 휠 위치 |
|---|---|---|---|
| 좌 | 0.158 m | **100 %** | −0.015 m |
| 우 | 0.155 m | **97 %** | +0.015 m |

## 14. 자국이 끊긴 점선 구덩이였다 — 하중 저역통과와 최대 깊이 채택 (기준일 2026-09-14)

**증상.** 자국은 렌더됐지만 이어진 홈이 아니라 **구덩이가 띄엄띄엄** 이어지고 까만 조각이 섞였습니다.

**원인.** 한 칸의 깊이는 **처음 밟는 순간의 하중 하나**로 정해졌습니다. 상류 규칙이 뒤따르는
통과를 `0.01^통과횟수` 로 줄여 더하기 때문입니다. 그런데 서스펜션 토크에서 얻는 하중이 주행 중
**137~662 N**(4륜 최대, 정상 182 N)으로 출렁여, 약한 순간에 밟힌 칸이 얕게 굳고 뒷바퀴가 지나가도
채워지지 않았습니다.

**고친 것** (둘 다 설정으로 켜고, 기본값은 상류 동작)

- **하중 저역통과** — 수직 하중을 **시뮬레이션 시간** 기준 0.3 s 지수이동평균으로 거릅니다.
  0.43 m/s에서 약 13 cm, 격자 2~3칸입니다.
- **최대 깊이 채택** — 같은 칸을 여러 번 밟으면 **가장 깊은 값**을 남깁니다.

## 15. 깊이가 하중에 선형이었다 — 하중의 2/3제곱으로 (기준일 2026-09-14)

**문제.** 하중-깊이 회귀가 원점을 지나는 직선이라 하중이 두 배면 깊이도 두 배였습니다. 14절의
「주행 중 깊이가 1.4~1.7배」 가운데 일부가 이 선형성입니다 — 주행 중 크게 읽히는 하중 피크가 그대로
깊이에 실렸습니다.

**근거.** 강성륜 Bekker 침하는

```
z = [ 3W / ((3 − n)·(k_c + b·k_φ)·√D) ]^(2/(2n+1))      →      z ∝ W^(2/(2n+1))
```

이고, 달 표토 기준값(Lunar Sourcebook, Soil B) n = 1이면 **W^(2/3)** 입니다. 같은 식이 우리 휠(폭 0.159 m ·
지름 0.427 m)과 하중 182 N에서 **21.6 mm**를 내, 11절의 교정값 0.020 m와 맞습니다.

**고친 것.** 회귀에 넣기 전에 하중을 `F_ref · (F / F_ref)^(2/3)` 로 바꿉니다(F_ref = 182.2 N = 자중 ÷ 4).
기준하중에서는 값이 그대로라 11절 교정이 유지됩니다 — 182.2 N에서 0.0201 m 그대로, 364 N에서 **1.587배**
(선형이면 2배).

**실제 Isaac에서 확인** — 14절과 같은 조건·같은 스크립트.

| 줄 | | 깊이 변동계수 | 거의 안 파인 구간 | 깊이 중앙값 · 최소 · 최대 |
|---|---|---|---|---|
| 좌 | 14절 후 | 0.37 | 8 % | 0.028 · 0.0074 · 0.044 m |
| 좌 | **하중^(2/3)** | **0.22** | **0 %** | **0.025** · 0.0140 · **0.034** m |
| 우 | 14절 후 | 0.27 | 14 % | 0.035 · 0.0150 · 0.042 m |
| 우 | **하중^(2/3)** | **0.20** | **0 %** | **0.030** · 0.0163 · **0.034** m |

주행 RTF 0.21~0.25, 멈춤 없음 — 성능 영향은 없습니다. 주행 중 깊이는 정지 교정의 1.2~1.5배로 줄었지만
여전히 시험 자료로 교정한 것은 아닙니다.

## 16. 고해상도 자국 — 1.5 cm 타일에 실제 휠 단면을 찍는다 (기준일 2026-09-14)

**왜.** 0.05 m 격자에서는 휠 폭이 3칸이라 자국 단면이 V자가 되고, 그라우저 무늬(주기 약 56 mm)는
원리상 나오지 않습니다. 해상도를 0.025 m로 올리면 시뮬레이션이 멈췄고(5절), 지금 해상도에서도 256만 정점
지형을 매번 다시 쓰느라 주행 중 RTF가 0.22였습니다(12절). 지형 전체를 1.5 cm로 올리면 6,400만 정점이라
불가능합니다. 방향은 **해상도 1.5 cm · 먼 자국도 유지 · 사실감 우선**으로 정했습니다.

### 먼저 잰 것 — 느린 원인은 정점 수가 아니라 쓰는 경로였다

실제 야드 장면(로버 정지)에 격자 메시를 두고, 매 반복 전 정점을 바꿔 쓰며 RTF를 쟀습니다.

| 정점 | USD 경로 | Fabric 경로 (CPU) | GPU(warp) → Fabric |
|---|---|---|---|
| 없음 (기준) | RTF 0.499 | | |
| 7만 (4 m) | 0.475 | 0.493 | **0.499** |
| 28만 (8 m) | **0.294** | 0.485 | **0.499** |
| 64만 (12 m) | **0.302** | 0.487 | **0.499** |

- **USD로 쓰면 28만 정점부터 RTF가 0.30** 으로 떨어집니다 — 주행 RTF 0.22와 같은 기전입니다.
- **Fabric(Omniverse 런타임 데이터 계층)으로 쓰면 64만 정점도 비용이 거의 없고**, 화면 캡처로 재질·그림자까지
  반영되는 것을 확인했습니다.
- 1 m 타일 400개(185만 정점)를 **정적으로** 두면 RTF 0.481 — 먼 자국을 고해상도로 남겨도 됩니다.
- 메시 구멍(`holeIndices`)으로 기존 지형을 가리는 방법은 화면에 반영되지 않아 쓰지 않았습니다.

### 구조

``` mermaid
flowchart LR
    A["휠 링크 4개<br/>위치·차축·회전각"] --> C["휠 근처 1 m 타일<br/>(1.5 cm, 없으면 생성)"]
    P["휠 메시 실측 단면<br/>그라우저 24 · 높이 19.1 mm"] --> D["휠 최저면을<br/>3 mm 간격으로 쓸어 찍기"]
    B["하중<br/>(서스펜션 토크, 하중^(2/3))"] --> D
    C --> D
    D --> E["둔덕 · 벽 무너짐"]
    E --> F["바뀐 타일만<br/>Fabric 갱신"]
    F -.->|"충돌 메시는 그대로"| G["PhysX 지형 충돌"]
```

- **실측 휠 단면** — 휠 메시에서 반경을 축방향 32칸 × 그라우저 위상 120칸으로 쟀습니다. 넓은 면에는 정점이
  모서리에만 있어 정점만 보면 그라우저 높이가 90 mm로 나오므로, 삼각형 내부를 채워 쟀습니다:
  림 194.2 mm · 팁 213.3 mm · **직선 그라우저 24개 · 높이 19.1 mm** · 가장자리 플랜지 200.4 mm.
- **그라우저 위치는 휠 회전각을 따릅니다.** 그래서 자국 간격이 슬립 s에 따라 `55.9 mm × (1 − s)` 로 줄고,
  슬립이 크면 무늬가 뭉개집니다 — 따로 모델링하지 않아도 나옵니다.
- **흙에 남는 몫** — 휠 형상의 그라우저 틈 중 40 %만 남깁니다(흙이 되흘러 듭니다). 판 흙의 10 %는 옆
  둔덕으로 보내고(추정), 휠 밖 벽은 60°를 넘으면 무너뜨립니다.
- **표시 지면 = 충돌면 + 27 mm.** 휠은 바뀌지 않은 충돌면 위에 서므로 그라우저 팁이 27 mm 잠긴 모습이
  됩니다 — 휠이 자국 안에 앉아 보입니다.
- 타일은 주행 내내 **남습니다**(먼 자국 유지). 타일 아래의 기존 지형은 가라앉혀 가립니다.

### 교정 — 실제 모듈을 가짜 지형에서 4륜 주행 (오프라인)

| 흙에 남는 그라우저 몫 | 평균 깊이 | 그라우저 자국 진폭 |
|---|---|---|
| 0.35 | 21.6 mm | 6.7 mm |
| **0.40 (채택)** | **20.9 mm** | **7.7 mm** |
| 0.45 | 20.3 mm | 8.6 mm |

목표는 깊이 Bekker 21.6 mm · Lunokhod 21~24 mm, 그라우저 자국 6~9 mm(단륜 시험 6.09 mm)입니다.
모듈 시험에서 슬립 0.1의 주기 **50.1 mm**(이론 50.3) · 슬립 0.3의 **39.0 mm**(이론 39.1) · 폭 0.164 m ·
타일 쓰기 누락 0 · 이음매 오차 0 · 호출당 3.4 ms를 확인했습니다.

### 실제 Isaac에서 확인

보드 EPOS, 구동 2.0 rad/s 직진, 5 s 창 스탬프 RTF.

| 항목 | 값 |
|---|---|
| 주행 RTF | **0.48~0.50** (0.05 m 방식 0.21~0.24, 변형 OFF 0.497) |
| 자국 계산 · 타일 갱신 | 호출당 1.0~1.9 ms · 0.1~0.3 ms |
| 평균 깊이 | 24~27 mm |

### 실측에서 나온 결함 둘 — 같은 지령을 다시 돌려 원인을 갈랐다

같은 지령이면 시뮬레이션이 결정적이라, 판을 바꿔도 자국과 카메라 위치가 같습니다. 이것을 대조 실험으로 썼습니다.

1. **타일 영역 경계를 따라 밝은 선.** 처음에는 기존 지형 가리기가 화면에 안 먹은 것으로 의심했지만, 쓰는
   경로를 바꿔도(Fabric · USD) **똑같이 보였고** 되읽은 값도 맞았습니다 — 가설이 틀렸습니다. 원인은 경계
   첫 줄 정점을 0.2 m 한꺼번에 내려 생긴 급경사가 **경계 정점의 부드러운 법선을 기울인 것**이었습니다.
   첫 줄만 2 mm 내리자 선이 사라졌습니다.
2. **자국 깊이가 줄을 따라 10~35 mm로 출렁임.** 휠의 물리 높이를 기준으로 찍었는데, 충돌 메시가 렌더 지형의
   근사라 휠 팁과 지형 사이가 직진 중에도 평균 6 mm · p95 15 mm 떴고(돌 위·선회 중에는 수백 mm), 하중 추정도
   ±16 mm 폭으로 출렁였습니다. **렌더 지형을 기준으로 찍고, 4 cm 넘게 뜬 휠은 찍지 않고, 하중 침하를 ±10 mm로
   묶어** 깊이 변동계수가 0.35~0.38 → **0.25~0.30**이 됐습니다.

!!! note "남는 것"
    - 남은 깊이 출렁임은 대부분 하중 추정 잡음입니다(서스펜션 토크 하중 산포 ±18 %).
    - 그라우저 자국 진폭 9~10 mm는 단륜 시험(6.09 mm)보다 큽니다.
    - 둔덕 비율과 벽 임계각은 정량 문헌이 없는 추정입니다.
    - **렌더 전용입니다** — 휠이 자국을 밟지 않으므로 슬립·견인 수치에는 반영되지 않습니다.
    - 타일이 계속 남으므로 아주 긴 주행에서는 정점이 쌓입니다(1 km에 약 600만 정점 추정).

## 17. 파라미터 조정 가이드 (기준일 2026-09-14)

설정은 lunaryard 환경 설정의 `terrain_manager.moon_yard.deformation_engine` 아래에 있습니다.
**무엇을 고치면 무엇이 바뀌는지**를 한곳에 모았습니다.

### 먼저 — 지금 쓰이는 값과 안 쓰이는 값

| 묶음 | 지금 동작에 영향 |
|---|---|
| A. 공통 (켜기 · 지연 · 하중 입력) | 항상 |
| B. 0.05 m 지형 경로 (`footprint` · 분포 · 회귀) | `track_tiles.enable: False` 일 때만 |
| C. `track_tiles` (1.5 cm 자국, 16절) | **지금 자국을 만드는 것** |

!!! warning "`track_tiles` 가 켜진 상태에서 B를 고치면 화면에 아무 변화가 없습니다"
    B로 되돌리려면 `track_tiles.enable: False` 로 둡니다 — 이때 주행 RTF는 0.22로 떨어집니다(12절).

### A — 공통

| 파라미터 | 현재 | 의미 | 조정 시 |
|---|---|---|---|
| `enable` | True | 변형 전체 스위치 | False면 자국 없음 |
| `delay` | 10.0 s (시뮬레이션 시간) | 시작 후 변형 시작까지 | 짧으면 스폰 낙하 충격이 구덩이로 남습니다(2 s일 때 21 cm) |
| `force_source` | suspension | 휠 하중을 어디서 읽나 | `contact` 는 정지 시 0으로 읽혀 **서 있으면 안 파이고 부딪히면 파입니다**(4절) |
| `suspension_joints` | FL · FR · RL · RR | 하중 토크를 읽을 조인트 | **휠 링크 목록과 순서가 같아야 합니다** — 틀려도 값이 그럴듯합니다 |
| `suspension_lever_arm` | 0.4908 m | 토크 → 힘 환산 팔 길이 | 로버 자산을 바꾸면 다시 계산 |
| `suspension_gain` | 1.78 | 4절 링크 보정(실측 교정) | 네 휠 합이 자중과 맞도록. 산포 ±18 % |
| `force_filter_tau` | 0.3 s | 하중 저역통과 | 늘리면 깊이가 고르고 충격에 둔해지고, 줄이면 출렁입니다 |
| 지형 크기·해상도 | 야드 설정 참조 | 자동 | 직접 고치지 않습니다 — 해상도 0.025에서 멈췄습니다(5절) |

### C — `track_tiles` (지금 켜진 1.5 cm 자국)

```
표시 지면       = 지형 + surface_offset
휠이 찍는 면     = 지형 + R + [원 + κ·(실측 휠 단면 − 원)] − δ
하중 침하 δ     = surface_offset · ((F / reference_load)^load_exponent − 1)
                  → [−max_less_sinkage, +max_extra_sinkage] 로 자름
```

그라우저 팁 깊이 ≈ `surface_offset + δ`, 그라우저 사이 둔턱은 ≈ `κ × 19.1 mm` 만큼 얕습니다.

**모양 (사실감 — 주로 여기를 만집니다)**

| 파라미터 | 현재 | 의미 · 효과 |
|---|---|---|
| `surface_offset` | 0.027 m | 자국 깊이의 기준. **+1 mm → 평균 깊이 약 +1 mm**(오프라인 0.024 → 18.0 mm, 0.027 → 20.9 mm). 크게 하면 휠·암석이 묻혀 보입니다 |
| `grouser_transfer` (κ) | 0.40 | 흙에 남는 그라우저 몫. **그라우저 무늬 깊이 ≈ κ × 19.1 mm**(0.35 → 6.7 · 0.40 → 7.7 · 0.45 → 8.6 mm, Isaac 실측 9~10 mm). 0 = 매끈한 홈, 1 = 휠 모양 그대로 |
| `berm_fraction` | 0.10 | 판 흙 중 옆 둔덕 비율 — **정량 문헌 없는 추정**. 0.25면 둔덕 약 11 mm로 과했습니다. 0 = 둔덕 없음 |
| `berm_width` | 0.03 m | 둔덕 폭 |
| `critical_angle_deg` | 60 | 휠 밖 벽 최대 경사. 낮추면 완만한 V, 높이면 날카로운 벽 |
| `relax_iterations` | 2 | 벽 무너뜨림 반복 수. 늘리면 임계각에 더 가깝게 수렴 |
| `wheel_profile` | 휠 단면 표 | **로버 자산을 바꾸면 휠 메시에서 다시 뽑습니다** |

**하중 반응**

| 파라미터 | 현재 | 의미 · 효과 |
|---|---|---|
| `reference_load` | 182.2 N | 이 하중(자중 ÷ 4)에서 δ = 0 |
| `load_exponent` | 0.6667 | 깊이 ∝ 하중^p (Bekker n = 1, 15절). 1이면 선형 — 하중 피크에서 과대 |
| `max_extra_sinkage` / `max_less_sinkage` | 0.010 / 0.010 m | δ의 한계. 넓히면 하중 차가 더 드러나지만 **하중 추정 잡음으로 줄을 따라 출렁입니다**(±16 mm로 풀었을 때 변동계수 0.35~0.38) |

**높이 기준 · 예외**

| 파라미터 | 현재 | 의미 · 효과 |
|---|---|---|
| `height_reference` | terrain | `terrain` = 렌더 지형 기준(권장). `wheel` = 물리 휠 높이 기준 — 충돌 메시 근사 오차(평균 6 mm · p95 15 mm)가 그대로 깊이 출렁임이 됩니다 |
| `lift_threshold` | 0.04 m | 지형에서 이보다 뜬 휠은 찍지 않습니다(돌 위·들림). 낮추면 요철에서 끊기고, 높이면 뜬 휠이 끌린 자국을 남깁니다 |

**해상도 · 타일**

| 파라미터 | 현재 | 의미 · 효과 |
|---|---|---|
| `samples_per_tile` | 67 | 1 m ÷ 67 = 1.49 cm. 100이면 1 cm — 정점 2.2배 |
| `tile_size` | 1.0 m | **지형 해상도(0.05 m)의 정수배여야 합니다** |
| `activation_margin` | 0.6 m | 휠에서 이 거리 안의 타일을 만듭니다. 너무 작으면 자국이 타일 영역 경계에 닿아 끊깁니다 |
| `max_substep` | 0.003 m | 쓸어 찍는 간격. 키우면 그라우저 팁(약 5 mm)을 건너뛰어 점무늬가 됩니다 |
| `max_jump` | 0.3 m | 한 번에 이보다 많이 움직이면(리셋·순간이동) 홈을 끌지 않습니다 |

**렌더 경로 (보통 건드리지 않습니다)**

| 파라미터 | 현재 | 주의 |
|---|---|---|
| `use_fabric` | True | False면 USD 경로 — 28만 정점부터 RTF 0.30 |
| `base_write` | fabric | `usd` 도 결과는 같고 25~28 ms(Fabric 9 ms) |
| `usd_write_calls` | 3 | 새 타일은 이 호출 수 동안 USD로 씁니다 |
| `base_hide_depth` | 0.2 m | 타일 아래 기존 지형을 가라앉히는 깊이 |
| `base_hide_edge_depth` | 0.002 m | 경계 첫 줄만 이만큼. **크게 하면 타일 영역 경계에 밝은 선이 다시 생깁니다** |

### B — 0.05 m 지형 경로 (`track_tiles` 를 끌 때만)

| 파라미터 | 현재 | 의미 |
|---|---|---|
| `footprint.width` | 0.21 | 횡 표본 수 = int(폭 / 0.05) + 1. **양 끝 표본은 늘 0**이라 파이는 칸 = 표본 − 2 → 0.21은 3칸(0.15 m) (13절) |
| `footprint.height` | 0.1804 | 접지 길이 L = 2√(2Rz − z²), z = 0.020 m |
| `wave_frequency` | 3.229 | **접지 길이 안의 그라우저 수** = N·L / (2πR). 한 바퀴 개수가 아닙니다 (6절) |
| `angle_of_repose` | 0.7854 (45°) | 가장자리 경사. 깊이를 최대 2.6배 좌우 |
| 회귀 기울기 · 절편 | 2.466×10⁻⁵ / −1.111×10⁻⁴ · 0 | 깊이 = 경계 × (진폭/2 × 파형 − 평균). 182.2 N에서 −0.0201 m. **절편은 0이어야 합니다** |
| `load_exponent` / `reference_load` | 0.6667 / 182.2 | 15절 |
| `accumulation` | max_depth | 같은 칸은 가장 깊은 값. `decay_sum` 일 때만 감쇠 비율을 씁니다 (14절) |

!!! warning "폭 · 안식각 · 회귀 기울기 · 길이 · `wave_frequency` 는 한 세트입니다"
    모두 침하 0.020 m를 가정합니다. 하나만 바꾸면 서로 어긋나므로 오프라인 재현 계산으로 다시 맞춥니다.
    설정에 있지만 **읽히지 않는 값**도 있습니다 — `gravity`, `footprint.shape`, `num_links` (6절).

### 목적별 조정

| 원하는 것 | 조정 |
|---|---|
| 그라우저 무늬를 더 선명하게 | `grouser_transfer` ↑ (0.5) |
| 자국 전체를 더 깊게 | `surface_offset` ↑ |
| 벽을 더 날카롭게 | `critical_angle_deg` ↑ (70) |
| 둔덕 없애기 | `berm_fraction: 0` |
| 깊이를 더 고르게 | `force_filter_tau` ↑ 또는 `max_extra/less_sinkage` ↓ |
| 하중에 따른 차이를 크게 | `max_extra/less_sinkage` ↑ (출렁임 감수) |
| 더 촘촘하게 | `samples_per_tile: 100` |

### 바꾸는 절차

1. **설정 파일을 고치지 않고 시험** — 실행 명령 뒤에 Hydra 덮어쓰기를 붙입니다.
   ```
   ++environment.terrain_manager.moon_yard.deformation_engine.track_tiles.grouser_transfer=0.35
   ```
2. **확정** — 설정 파일을 고치고, **시뮬레이터가 실제로 읽는 OmniLRS 설치본의 설정도 같은 파일인지** 확인합니다.
   저장소 쪽만 고치면 조용히 옛 값으로 돕니다.
3. **검증** — 오프라인 시험(수 초: 깊이 · 주기 · 폭 · 이음매)을 먼저 보고, Isaac에서 직진 주행 → 후방 카메라 →
   깊이 · 그라우저 · 폭 · RTF를 잽니다. **같은 지령이면 시뮬레이션이 결정적**이라 전후 사진을 그대로 비교할 수
   있습니다. RTF는 **헤더 스탬프**로 잽니다 — 수신 주기로 재면 물리가 멈춘 상태를 정상으로 봅니다(12절).
