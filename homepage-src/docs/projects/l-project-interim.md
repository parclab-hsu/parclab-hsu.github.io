# 현대자동차 L-Project — 중간 보고

:material-circle:{ style="color:#2e9e44" } **진행중** · 달 탐사 로버 12축 HILS 시스템 · 보고 기준일 **2026-09-22** (최초 2026-08-22)

!!! abstract "요약"
    **3계층 폐루프가 실기에서 성립했습니다.** Navigation(Jetson Orin) — HILS 보드(STM32H7,
    micro-ROS) — 시뮬레이션 PC(Isaac Sim)를 잇는 12축 구동 폐루프가 주기뿐 아니라 **값까지
    일치**하는 것을 확인했습니다.

    소프트웨어 측 위험은 상당 부분 제거되었고, 남은 것은 **실물 하드웨어가 있어야만 확인
    가능한 항목**과 **플랜트 물성의 근거 확보**입니다. 아래 「확인되지 않은 것」을 함께
    읽어 주시기 바랍니다 — 이 보고서는 확인된 범위와 그렇지 않은 범위를 구분해 적었습니다.

## 1. 과제 개요

4륜 독립조향(4WS) + 액티브 서스펜션의 **12축 달 탐사 로버** 구동계를, 실물 로버 없이
검증할 수 있는 HILS(Hardware-In-the-Loop Simulation) 환경으로 구축하는 과제입니다.

| 계층 | 담당 | 구현 |
|---|---|---|
| Navigation | NVIDIA Jetson Orin | ROS 2 Humble — 주행 제어·오도메트리·조종·헬스 감시 |
| **제어기** | HILS 보드 (STM32H723) | FreeRTOS + micro-ROS(XRCE-DDS), Drive Interface 추상화 |
| 플랜트 | 시뮬레이션 PC | Isaac Sim 5.0 + OmniLRS 월면 지형 |

**핵심 설계 원칙은 「보드가 항상 루프 안에 있다」입니다.** 실 구동이든 시뮬레이션이든
Navigation의 명령은 반드시 보드의 Drive Interface를 거칩니다. 그래야 제어 주기·안전
로직·인터페이스를 두 모드에서 **같은 코드로** 검증할 수 있습니다.

## 2. 중간 시점까지 확인된 것

### 2.1 3계층 폐루프 — 값 일치 확인

`rover_control → HILS 보드 → Isaac Sim → 보드 → rover_state` 경로에서, 정상상태 주행 중
구동 4축을 동시에 측정한 결과입니다.

| 측정 지점 | 구동 4축 [rad/s] |
|---|---|
| 시뮬레이터 실측 | `+2.319 · +2.346 · +2.333 · +2.337` |
| 보드 피드백 | `+2.318 · +2.346 · +2.332 · +2.332` |

`/cmd_vel` 0.5 m/s 지령에 대해 오도메트리 `/odom` 은 **+0.465 m/s** 를 복원했습니다.
조향 4축도 함께 일치합니다.

!!! note "이 확인에 이르기까지 두 층의 결함을 열었습니다"
    **① 보드의 관절 상태 발행이 한 번도 성공한 적이 없었습니다.** 12축 계약으로 조인트명을
    확정하면서 메시지가 약 684 B가 되었는데, micro-ROS 전송 계층의 MTU가 512였습니다.
    Best-effort 전송은 단편화하지 않으므로 매 주기 실패하고 있었고, 반환값을 확인하지 않아
    **보드에 아무 흔적이 남지 않았습니다.** 라이브러리를 MTU 1024로 재빌드해 계약을 유지했고,
    재플래시 후 50.005 Hz로 처음 흘렀습니다.

    **② 보드가 CAN 백엔드로 부팅합니다.** CAN 버스에 아무것도 없는 상태에서는 구동이
    성립할 수 없었습니다. 런타임에 백엔드를 바꾸는 토픽을 신설해 해결했습니다.

### 2.2 Jetson 실기 배포

ROS만 설치된 Jetson에서 시작해 조이패드 조종까지 명령 경로 전 구간을 세웠습니다.
이 과정에서 **회귀 시험 8종이 계속 통과하는 상태에서** 결함 5건이 드러났습니다 — 전부
개발 PC가 우연히 만족시키던 환경·하드웨어 전제였습니다.

| 결함 | 성격 |
|---|---|
| 배포 스크립트 22개의 실행 권한 누락 | 개발측 파일시스템(CIFS)에서는 보이지 않음 |
| `set -u` 와 ROS 환경 스크립트 충돌 | 배포 첫 줄에서 중단 |
| 선택적 의존성 부재가 배포 전체를 중단 | 기본 이미지에 해당 도구 없음 |
| 펌웨어 발행 주기 오차 (1.536 Hz / 2 Hz 계약) | 상대 지연을 절대 주기로 사용 |
| 조이패드 런치가 패드를 열 수 없음 | 장치 경로를 이름 파라미터에 전달 |

**시사점 — 자동 회귀는 환경 전제를 검증하지 못합니다.** 실기 배포는 그 자체로 하나의
검증 단계이며, 대체할 수 없습니다.

### 2.3 월면 환경 플랜트

무한 평면에서 **OmniLRS lunaryard 절차 생성 월면 지형**으로 옮겼습니다. 자산의 물리
특성이 전부 플레이스홀더(21개 강체 모두 관성 `1e-4` 고정, 로버 전체 30 kg)여서 구동축이
아예 회전하지 않던 문제를 해결했습니다.

| 항목 | 값 | 근거 |
|---|---|---|
| 총질량 | 450 kg | NASA VIPER surface operations mass 참조 |
| 관성 | 형상 자동 계산 | 플레이스홀더가 자동 계산을 막고 있었음 |
| 중력 | 1.62 m/s² | 달 |
| 지형 마찰 | static 0.90 / dynamic 0.70 | Apollo 토질 시험(내부 마찰각 42°), 그라우저 휠은 토양 내부 전단 |

### 2.4 기구학 모델 정정

**조향축 오프셋이 반영되어 있지 않았습니다.** 기구 도면이 없어 시뮬레이션 자산의 조인트
좌표에서 직접 실측한 결과, 휠 접지점이 조향축보다 **0.1271 m 바깥쪽**(스크럽 반경)에
있었습니다. 조향하면 휠이 조향축 둘레로 돌기 때문에, 고정 위치로 계산하면 선회에서
**조향각 최대 8.2°·휠 속도 9.3 %** 어긋납니다.

!!! warning "직진 시험으로는 드러나지 않는 종류였습니다"
    직진과 동위상(crab steering) 주행에서는 속도장이 균일해 **차이가 정확히 0** 입니다.
    선회 시험을 해야만 나타납니다.

함께 반영한 것:

- **동위상·역위상 조향 모드** — 역위상은 앞뒤 반대 조향(선회), 동위상은 네 바퀴 같은 각
  (자세 유지 사선 이동). 조종 배치를 좌스틱=방향 / 우스틱=스로틀로 변경
- **선회 포락선** — 휠 각속도 한계와 횡가속 한계(0.55 m/s², 견인 기준)에서 유도.
  참조 차량 식과 달리 **속도가 오를수록 좁아집니다**(조향 ±90°라 최소 선회반경이 없음)

### 2.6 「슬립 49 %」의 정체 — 슬립이 아니었습니다 (2026-08-25)

직전 보고(2026-08-22)에서 **가장 중요한 미해결 항목**으로 올렸던 것입니다. 월면토 마찰
계수를 80 % 올렸는데 슬립이 **소수점까지 같았습니다**(49.0 / 49.1 %). 마찰이 만든 값이
아니라는 것까지는 알았지만 원인을 몰랐습니다.

**원인은 플랜트가 아니라 측정이었습니다.** 속도를 40배(0.1~4.0 rad/s) 흔들어도 슬립이
**속도와 무관하게 일정**했는데, 평지 정상상태에서 필요한 견인력은 굴림 저항뿐이라 거의
0입니다. 거기서 49 %가 속도와 무관하게 나온다면 그것은 미끄러짐이 아니라 **배율**입니다.

같은 노드가 내는 **위치 변위/시간과 속도가 정확히 2배 어긋나 있었습니다**(비 0.4987).
시뮬레이터가 실시간의 약 절반으로 돌고 있는데, 측정 도구가 이동 경로를 **벽시계 시간**으로
나누고 있었습니다. 실시간 배율 0.4994가 그대로 `1 − 0.4994 = 0.5006` 의 슬립으로 둔갑한
것입니다.

**시뮬레이션 시간으로 다시 재니** 8배 속도 범위에서 슬립 **−0.011 ~ +0.001**, 유효 굴림
반경 비 **1.0097**, 위치/속도 비 **1.0017** 로 일치했습니다. 침하와 차체 끌림 가설은
전부 배제됐습니다.

!!! note "마찰 A/B 결과는 여전히 유효합니다"
    애초에 물리량을 재고 있지 않았으므로 **마찰이 안 듣는 것이 정상이었습니다.**
    측정 도구를 시뮬레이션 시간 기준으로 바꾸고, 시뮬레이션 시간이 진행하지 않으면
    측정을 기각하도록 했습니다. 계기판에 **실시간 배율을 상시 표시**합니다 — 같은 착오를
    되풀이하지 않으려면 화면에 늘 떠 있어야 합니다.

### 2.7 실기 조종과 보드 기구학 (2026-09-16 ~ 09-22)

**기구학을 보드가 소유하도록 옮겼습니다.** 상위는 명령을 중재하고, 4WS 역기구학과 12축
실시간 제어는 보드가 맡습니다. 조향에는 두 겹의 한계를 두었습니다 — 자산 조인트 한계
±90°는 바깥 울타리로 남기고, 운용 정책은 **코너별로 거울인 −30°~+60°** 입니다.

**보드가 낸 12축을 독립 구현한 역기구학과 대조했습니다.** 같은 계산을 베끼지 않고 1차
원리에서 다시 구현해야 구현이 틀려도 사이좋게 틀리는 일을 막을 수 있습니다.

| 항목 | 결과 |
|---|---|
| 판정 가능한 표본 | 13,443 |
| 일치 | **13,260 (98.6 %)** |
| 터보 최대 `v 1.000 m/s` | 구동 4.684 rad/s (기대 4.688) |
| 제자리 회전 조향각 | **±55.30° · 오차 0.0001** |

정지 중 조향 유지, 선회 포락선 개입, 지령 변동 구간은 **판정 보류**로 분리해 셉니다 —
이것을 섞으면 정상 동작이 전부 불일치로 보입니다.

### 2.8 플랜트 운용에서 드러난 것 (2026-09-18 ~ 09-22)

**시뮬레이터가 멈춘 것처럼 보였으나 원인은 어댑터 부재였습니다.** 12축 배열을 자산
그래프로 잇는 중간 노드가 떠 있지 않았습니다. 보드는 피드백이 끊겨도 지령을 계속 내기
때문에(타임아웃 처리가 없습니다) **계기판은 정상이고 시뮬레이터만 조용히 멈춥니다.**
상시 기동 서비스로 묶어 재발을 막았고, 복구 후 실주행 **6.375 m** 를 확인했습니다.

**로버가 월석을 통과했습니다.** 콜라이더는 **자산에 이미 있었고**, 막고 있던 것은 암석을
뿌리는 인스턴싱 방식이었습니다. 실제 개체를 만드는 방식으로 바꾸어 충돌이 성립합니다.
판정은 눈이 아니라 **이론 거리 대비**로 했습니다 — 통과 시 **0.84**, 해결 후 **0.09**
(지령 2.339 rad/s에 3 cm 전진). 성능 대가는 실시간 배율 0.4993 → 0.4953(0.8 %)뿐입니다.

## 3. 확인되지 않은 것

!!! danger "이 절이 이 보고서에서 가장 중요합니다"
    아래는 **아직 근거가 없는 항목**입니다. 확인된 것과 구분해 읽어 주시기 바랍니다.

### 3.1 플랜트가 장시간 운전에서 느려집니다 (2026-09-22)

컨테이너를 **21시간** 연속 돌리자 그래픽 자원 할당이 깨지면서 실시간 배율이
**0.48 → 0.12** 로 주저앉았습니다. 재기동하면 완전히 회복됩니다(렌더 오류 300,948 → 0).

**고약한 점은 물리가 계속 돈다는 것입니다.** 시뮬레이션 시간은 멈추지 않고 토픽도 계속
나오므로 **「좀 느리네」로만 보입니다.** 오류 발생 빈도도 시간이 지나며 줄어드는데, 이는
회복이 아니라 **루프 자체가 느려진 결과**입니다.

배제한 것 — 그래픽 메모리 여유(6.4 GB), 커널 오류 0건, 호스트 메모리 여유(72 GB),
파일 디스크립터(412/2450), 공유 메모리(1 %), 디스플레이 연결. **원인을 좁히지
못했습니다.** 공통 조건은 장시간 연속 운전뿐입니다.

**조치는 절차입니다** — 성능을 재기 전에 실시간 배율과 렌더 오류 건수를 먼저 봅니다.
장시간 돌린 컨테이너에서 잰 성능 수치는 쓰지 않습니다.

### 3.2 안전 공백 — 조종 링크 두절 감지

조이패드가 절전에 들어가거나 무선이 끊겨도, 드라이버가 마지막 값을 20 Hz로 계속
재발행하기 때문에 **명령 흐름이 끊기지 않습니다.** 기존 워치독은 명령이 *끊길 때*
동작하므로 이 경우 걸리지 않고, 데드맨을 쥔 채 두절되면 **마지막 주행 명령이 무한
반복됩니다.**

현재는 운용 규칙(유선 사용, 비상 정지 상시 대기)으로만 막고 있으며, **실물 드라이브를
연결하기 전에 반드시 닫아야 하는 항목**으로 등재해 두었습니다.

## 4. 결함 관리에서 얻은 것

이 과제에서 반복해 확인된 패턴을 기록해 둡니다. 산출물만큼 이 경험이 이전 가능한
자산이라고 판단합니다.

**① 실행해야만 드러나는 층이 있습니다.** 정적 검사와 대역 노드 리허설 26항목을 전부
통과한 상태에서 실기동 1분 만에 드러난 결함이 있습니다. 예를 들어 브리지가 명령을
Best-effort로 발행하는데 시뮬레이터는 Reliable로만 구독해 **명령이 단 한 건도 전달되지
않던** 경우, 피드백 방향은 멀쩡히 흘러서 자산이나 배선을 의심하게 만들었습니다.
**QoS도 토픽명·필드·단위와 같은 급의 계약**이라는 것을 계약 문서에 못박았습니다.

**② 대역 노드로는 원리적으로 잡을 수 없는 층이 있습니다.** 위 MTU 초과는 Linux 프로세스로
만든 대역 노드에는 XRCE 전송 계층이 아예 없으므로, 어떤 스텁으로도 재현되지 않습니다.

**③ 측정 절차가 없는 결함을 만들어냅니다.** 여러 지점을 순차로 확인하면 샘플 간격이
벌어져 물리적으로 불가능한 데이터가 나오고, 그것이 멀쩡한 코드를 결함으로 지목하게
만듭니다. 이 과제에서 확인된 「상태 오판」 8건은 **전부 제품이 아니라 점검 도구·측정
절차 쪽**이었습니다. 이후 판정 도구에는 자체 시험과 무효 구간 기각 로직을 넣고 있습니다.
