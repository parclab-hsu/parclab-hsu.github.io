# 9주차 현장 사례노트 · 입력·클럭·인터럽트

> 이 자료는 강의 내용을 AMR, 전동킥보드, 로버, 차량 ECU 사례로 연결하기 위한 설명 노트다. 학생이 왜 이 내용을 배우는지 이해하도록 실제 고장과 설계 판단 중심으로 사용한다.

## 현장 맥락

- 사례 주제: EXTI, 클럭, 엔코더 이벤트
- 실습 키트는 작지만, 판단 구조는 실제 모빌리티 ECU와 같다.
- 현장에서는 정상 동작보다 고장 재현, 로그 확보, 안전 정지가 더 중요하다.

## 사례 시나리오

| 상황 | 관찰 증상 | 의심 원인 | 확인 방법 |
|---|---|---|---|
| 전원 인가 직후 이상 동작 | LED, 모터, 통신이 불안정 | 전원 레일, 그라운드, 초기화 순서 | 전압 측정과 부팅 로그 확인 |
| 명령은 들어오나 출력이 없음 | PWM 또는 모터 반응 없음 | 핀 설정, 드라이버 enable, 보호 상태 | GPIO, PWM, Fault 핀 확인 |
| 값이 튀거나 로그가 흔들림 | ADC, RPM, UART 데이터 불안정 | 노이즈, 샘플링 타이밍, 접지 문제 | 오실로스코프와 Teleplot 비교 |
| 반복 실험마다 결과가 다름 | 팀마다 수치 차이 큼 | 부품 오차, 배선 길이, 설정값 불일치 | 조건표와 사진으로 재현성 확인 |

## 교수자 설명 포인트

1. 학생이 보는 작은 오류를 실제 제품에서는 리콜, 안전사고, 서비스 비용으로 연결해 설명한다.
2. 데이터 로그는 디버깅 도구이자 제품 품질을 설명하는 언어라고 강조한다.
3. 하드웨어, 펌웨어, 제어 알고리즘을 분리해서 원인을 좁히는 절차를 반복시킨다.
4. AI 도구는 가설 생성에는 유용하지만, 최종 판단은 측정값과 회로 근거로 검증해야 한다.

## 토론 질문

- 이 문제가 주행 중 발생하면 로봇은 즉시 멈춰야 하는가, 제한 속도로 움직여도 되는가?
- 사용자가 볼 수 있는 오류 메시지는 무엇이어야 하는가?
- OTA로 고칠 수 있는 문제와 하드웨어 수정이 필요한 문제를 어떻게 구분할 것인가?
- 다음 설계에서는 어떤 센서, 보호회로, 로그 항목을 추가할 것인가?

## 보고서 연결 문장

- "본 실험은 EXTI, 클럭, 엔코더 이벤트를 AMR ECU 관점에서 검증하기 위해 수행하였다."
- "측정 결과는 설계값과 비교해 오차 원인을 하드웨어, 펌웨어, 제어 파라미터로 구분하였다."
- "최종 시스템에서는 고장 감지 후 안전 상태로 전이하고, 로그를 남겨 원인 분석이 가능해야 한다."
