# 7주차 운영 키트 — 제어공학 기초와 PI 속도제어

### 교안 정보

| 항목 | 내용 |
|---|---|
| 교과목 | 모빌리티 전자제어유닛 실습 (3학점 · 전공) |
| 대상 | 미래모빌리티학과 3~4학년 |
| 차시 | 7주차 / 15주차 · 180분 |
| 강의실 | Physical AI 실습실 |
| 관련 자료 | 상세 강의자료 07번 · 과제집 18번 · 배포용 워크시트 O·P |

### 학습목표

이 시간이 끝났을 때 학생은 다음을 수행할 수 있다.

1. open-loop와 closed-loop 제어를 구분한다.
2. P, I, PI 제어의 장단점을 설명한다.
3. Teleplot 또는 UART 데이터를 이용해 속도 응답을 관찰한다.

### 핵심 질문

- 속도 명령만 주면 왜 실제 속도가 항상 같지 않은가?
- P 제어만 쓰면 정상상태 오차가 남는 이유는?
- I 게인이 너무 크면 어떤 현상이 생기는가?

### 지도 중점

6주차까지가 "정해진 duty를 정확히 내보내는 방법"이었다면, 7주차는 **"duty를 스스로 찾아가게 만드는 방법"** 이다. 이 주차의 목표는 PI 공식 암기가 아니라 **응답을 숫자로 평가해 게인을 고르는 절차**다.

> 📌 이 주차는 **8주차 중간 설계 리뷰 직전**이다. 여기까지의 산출물(전력 예산·모터 사양·6-step 표·PI 게인)이 리뷰 자료가 된다는 것을 도입부에서 알린다.

### 1. 180분 진행 대본

#### 블록 1 · 0~45분 — 피드백이 필요한 이유

**목표** — "명령을 줬는데 왜 그대로 안 되는가"를 실물로 먼저 보여 준다.

1. (5분) **6주차 과제 피드백.**

   > 🗣️ "지난주까지는 duty를 **여러분이** 정했습니다. 오늘은 duty를 **제어기가** 정합니다."

2. (10분) **개루프의 한계 — 실물 시연.** 고정 duty로 모터를 돌린 뒤, 축에 손으로 마찰을 준다.

   > 🗣️ "duty는 그대로입니다. 그런데 속도가 떨어졌죠. 로버가 경사에 진입하면 이 일이 그대로 벌어집니다."

   > ✍️ 판서: `reference → error → controller → plant → feedback`

3. (10분) **P 제어.** 오차에 비례한 입력. 빠르지만 **정상상태 오차가 남는다.**

   왜 남는지 한 줄로 설명한다.

   > 🗣️ "오차가 0이 되면 P 항도 0이 됩니다. 그런데 모터를 돌리려면 duty가 필요하죠. 그래서 **오차가 완전히 0이 될 수 없습니다.**"

4. (10분) **I 제어.** 오차를 누적해 남은 오차를 없앤다. 대신 **wind-up** 위험.

5. (10분) **PI와 제한 조건.** 로버 경사 등판에서의 부하 변화. duty 상한, 전류 제한, 온도 제한이 제어기 위에 있다는 것을 명확히 한다.

   > ⚠️ **제어기는 보호 로직보다 아래에 있다.** 과전류·과열·센서 이상이면 제어기 출력과 무관하게 차단된다. 12주차에서 하드웨어로 한 겹 더 쌓는다.

> ✅ **이 블록이 끝났을 때** — 학생이 "부하가 변해도 속도를 유지하려면 피드백이 필요하다"를 눈으로 확인한 상태.

#### 블록 2 · 45~90분 — 이산 PI와 코드 결함 찾기 (활동 1·2)

**목표** — 교과서의 연속 수식을 **1ms마다 도는 코드**로 옮기게 한다.

1. (15분) **활동 1 — 이산 PI 유도** (워크시트 O 상단)

   > ✍️ 판서
   > ```text
   > error[k] = ref[k] − fdb[k]
   > I[k]     = I[k−1] + Ki × Ts × error[k]
   > u_raw[k] = Kp × error[k] + I[k]
   > u[k]     = clamp(u_raw[k], u_min, u_max)
   > ```

   > 🗣️ "적분에 `Ts`가 곱해져 있죠. 제어 주기를 1ms에서 0.5ms로 바꾸면 어떻게 됩니까? 같은 Ki인데 **적분이 절반 속도로** 쌓입니다."

   블록도와 코드 변수를 연결시킨다.

   ```text
   RpmRef → RpmErr → Pterm ┐
                            ├→ PIterm → VoltageRef → Duty → Motor → RpmFdb
                     Iterm ┘
   ```

2. (18분) **활동 2 — baseline 코드 결함 찾기** (워크시트 O 중단)

   **이 주차의 핵심 활동이다.** `week07_pi_baseline.c`를 배포하고 **정상 코드는 아직 주지 않는다.**

   힌트를 순서대로 준다. 처음부터 다 말하지 않는다.

   | 단계 | 힌트 |
   |---|---|
   | 1 | "포화가 걸린 상태로 3초 두었다가 지령을 낮추면 어떻게 될까요?" |
   | 2 | "출력에는 상한이 있습니다. **적분항 자체**에는요?" |
   | 3 | "제어 주기는 1ms입니다. 코드에 곱해진 상수를 읽어 보세요." |

   찾아야 할 결함 두 가지.

   | 결함 | 증상 |
   |---|---|
   | 적분항에 제한이 없다 (출력만 clamp) | 포화 후 지령을 낮춰도 **overshoot가 오래 지속** |
   | 주기 상수 불일치 (`0.0005f` ↔ 실제 1ms) | 실효 `Ki`가 의도의 **절반** |

   > 🗣️ "실무에서 만나는 코드는 대부분 이렇습니다. **돌아가긴 하는데 이상한** 코드요. 무엇이 이상한지 말로 설명할 수 있어야 고칠 수 있습니다."

3. (12분) **anti-windup 세 가지 방법**을 비교한다.

   | 방법 | 내용 | 특징 |
   |---|---|---|
   | conditional integration | 출력이 포화 방향으로 더 커질 때 적분 중지 | 구현이 단순 |
   | integrator clamp | `Imin ≤ Iterm ≤ Imax` | 가장 흔함, 한계값 선정이 중요 |
   | back-calculation | 포화 전후 차이로 적분항을 되돌림 | 부드럽지만 튜닝 항목이 하나 더 |

   > ⚠️ `u_min`/`u_max`는 자료형 범위가 아니라 **전류·온도·시험 조건에서 허용한 PWM 범위**여야 한다.

#### 블록 3 · 90~155분 — 튜닝 실험 (활동 3·추가 실습)

> ⚠️ **시작 전 안전 확인.** 바퀴가 공중에 떠 있는지, 전류 제한과 duty 상한이 걸려 있는지 팀별로 교수가 직접 확인한 뒤 전원을 켜게 한다.

**목표** — "그래프가 좋아 보인다"가 아니라 **숫자로 고르게** 한다.

1. (10분) **활동 3 — Teleplot 출력 설계** (워크시트 P 상단)

   ```text
   >RpmRef:300
   >RpmFdb:275
   >Duty:1200
   ```

   > 🗣️ "무엇을 같이 찍어야 원인을 구분할 수 있을까요? 지령만 보면 잘 따라가는지 모르고, 피드백만 보면 왜 그런지 모릅니다."

   최소 4종을 함께 출력하게 한다 — `RpmRef`, `RpmFdb`(raw), `RpmFdb`(filtered), `Duty`. 전류를 읽을 수 있으면 추가한다.

   > ⚠️ 6주차 UART 예산을 상기시킨다. 1ms마다 전부 찍으면 처리량을 넘는다. **10ms 주기 출력**으로 시작한다.

2. (30분) **단계적 튜닝** (워크시트 P 중단)

   순서를 칠판에 고정하고 그대로 따르게 한다.

   ```text
   1  바퀴 공중 부양, 전류·duty 제한 낮게 설정
   2  Ki = 0, 작은 Kp부터 — 반응성과 진동 관찰
   3  정상상태 오차가 줄도록 Ki를 조금씩 증가
   4  무부하 + 부하 변화 + 명령 step에서 지표 기록
   5  과전류·센서 단선·stall에서 보호 로직이 제어기보다 우선하는지 확인
   ```

   **Kp·Ki 3조합**을 같은 조건에서 비교하고 표를 채우게 한다.

   | 지표 | 어떻게 읽는가 |
   |---|---|
   | 상승시간 | 지령의 90%에 처음 도달하는 시간 |
   | overshoot | 최대값이 지령을 넘은 비율 |
   | 정착시간 | 허용 오차 대역에 머무르기 시작하는 시간 |
   | 정상상태 오차 | 안정 후 남은 차이 |
   | 최대 전류 | 과전류 임계 대비 여유 |

   판서로 판단 예를 보여 준다.

   ```text
   A  Kp 1.0 / Ki 5     오차 6.0%   → 요구(±5%) 미달
   B  Kp 2.0 / Ki 10    오버슈트 8%, 최대 2.6A   → 채택
   C  Kp 4.0 / Ki 20    오버슈트 24%, 최대 4.8A  → 임계 5.0A에 근접, 여유 없음
   ```

   > 🗣️ "C가 제일 빠릅니다. 그런데 왜 안 고릅니까? **요구사항과 전류 여유**로 고르는 겁니다. 빠른 게 좋은 게 아니라 **요구를 만족하면서 여유가 있는 게** 좋은 겁니다."

3. (15분) **포화 실험 — wind-up을 직접 만든다** (워크시트 P 하단)

   duty 상한을 30%로 낮추고 500rpm을 지령해 3초간 포화시킨 뒤, 지령을 200rpm으로 낮춘다.

   > 🗣️ "지금 무슨 일이 일어났습니까? 지령은 200인데 속도가 210까지 올라가서 한참 안 내려오죠. **적분항이 포화 중에도 계속 쌓인** 겁니다."

   그다음 anti-windup을 적용하고 **같은 실험을 반복**해 개선을 확인시킨다.

4. (10분) **좌우 2채널과 직진 유지.**

   > 🗣️ "제어기가 두 개입니다. 같은 명령을 줘도 마찰과 무게 배분이 달라서 로버가 휩니다."

   | 단계 | 내용 |
   |---|---|
   | 1단계 | 좌우 각각 **독립 PI**. 적분항과 anti-windup은 **채널마다 따로** |
   | 2단계 | 남는 직진 편차를 `vL − Δ/2`, `vR + Δ/2`로 나눠 보정 |

   > ⚠️ 한 채널이 duty·전류 한계에 걸리면 그쪽만 명령을 못 따라가 **로버가 돌아간다.** 한 채널이 포화되면 **양쪽 명령을 함께 낮춰** 좌우 비율을 유지한다.

   로그에는 `RpmRefL/R`, `RpmFdbL/R`, `DutyL/R`을 **함께** 남기게 한다. 한쪽만 보면 편차의 원인을 구분할 수 없다.

**교수는 돌아다니며 두 가지만 확인한다**
- **같은 초기조건**에서 세 조합을 비교했는가 (조건이 다르면 비교가 아니다)
- 그래프만 붙이지 않고 **지표를 수치로** 적었는가

> ✅ **이 블록이 끝났을 때** — 각 팀이 근거를 대며 게인 한 조합을 고른 상태.

#### 블록 4 · 155~180분 — 필터 지연과 과제

1. (10분) **속도 측정과 필터 지연.**

   홀 edge 간격으로 계산한 RPM은 **저속에서 갱신이 드물고 양자화가 크다.** 그래서 필터를 걸고 싶어진다.

   > 🗣️ "노이즈가 싫어서 필터를 세게 걸면 어떻게 됩니까? 파형은 예뻐집니다. 그런데 **피드백이 늦게 도착합니다.** 늦은 정보로 제어하면 진동합니다."

   raw RPM, filtered RPM, reference, duty를 **동시에 기록**해 필터의 이득과 지연을 함께 판단하게 한다.

2. (7분) **형성평가 4문항**

   1. 제어 주기를 10ms에서 5ms로 바꾸면 적분 계산에서 무엇을 확인해야 하는가?
   2. 출력 포화 후 overshoot가 오래 지속되는 현상을 설명한다.
   3. RPM 필터를 강하게 할 때 노이즈 외에 생기는 부작용은?
   4. 좌우 중 한 채널만 포화될 때 로버에 생기는 현상과 대응은?

3. (5분) **과제 안내**

   > 7주차 과제 — PI 속도제어 튜닝 보고 (Kp·Ki 3조합 비교 + 선택 근거 + anti-windup 검토)
   > 형식: PDF 2~3장 + 그래프 캡처 · 파일명 `W07_팀명_이름.pdf`
   > 마감: 다음 주 수업 시작 전 · 1일 지각당 20% 감점
   > 배점 5점 — 동일 조건 정량 비교 2 / 선택 근거가 요구사항 수치와 연결 1 / 포화 상황 실험 재현 1 / 코드의 적분 처리 문제 지적 1

   > 🗣️ "그래프만 붙이면 2점입니다. **상승시간·오버슈트·정착시간·정상상태 오차를 숫자로** 적어야 합니다."

4. (3분) **다음 주 예고**

   > 🗣️ "다음 주는 **중간 설계 리뷰**입니다. 새로 배우는 내용이 아니라 지금까지 만든 것을 모아 발표합니다. 전력 예산, 모터 사양, 6-step 표, 오늘의 게인이 전부 자료가 됩니다."

### 2. 판서 목록

1. `reference → error → controller → plant → feedback`
2. P만 쓰면 오차가 남는 이유 (오차 0 → P항 0)
3. 이산 PI 4줄 (`error` / `I` / `u_raw` / `clamp`)
4. 블록도-변수 대응 (`RpmRef` `RpmErr` `Pterm` `Iterm` `PIterm` `VoltageRef`)
5. anti-windup 3방법 비교
6. 튜닝 절차 5단계
7. Kp·Ki 3조합 판단 예 (A 오차 6% / B 채택 / C 전류 4.8A)

### 3. 자주 나오는 질문과 답

| 학생 질문 | 답 |
|---|---|
| "Kp를 아주 크게 하면 오차가 없어지지 않나요?" | 오차는 줄지만 0이 되지 않고, **진동과 전류 피크**가 커진다. 정상상태 오차를 없애는 것은 I의 역할이다 |
| "Ki만 크게 하면 안 되나요?" | 적분이 빨리 쌓여 **overshoot와 wind-up**이 커진다. P가 먼저 반응하고 I가 마무리하는 구조다 |
| "제어 주기는 짧을수록 좋나요?" | 짧으면 반응은 좋지만 CPU 부담이 늘고, **주기 안에 코드가 안 끝나면**(overrun) 오히려 나빠진다. 11주차에서 다시 다룬다 |
| "필터를 걸었더니 그래프가 예뻐졌는데요?" | 파형이 예쁜 것과 제어가 좋은 것은 다르다. **지연이 늘면 진동한다.** raw와 filtered를 함께 봐야 한다 |
| "게인은 계산으로 못 구하나요?" | 모델이 있으면 초기값은 계산할 수 있다. 다만 마찰·부하 변동 때문에 **실측 튜닝이 반드시 따른다** |
| "좌우 게인을 다르게 잡아도 되나요?" | 된다. 다만 **같게 시작**하고, 다르게 했다면 그 이유를 기록한다 |

### 5. 안전 점검

**이번 주는 모터가 폐루프로 계속 돈다.** 제어기가 스스로 duty를 올리므로 6주차보다 위험이 크다.

- 🔴 **바퀴 또는 축을 반드시 공중에 띄운다.** 지면 주행은 15주차 절차를 따른다
- 🔴 **전원을 켜기 전에 duty 상한과 전류 제한을 먼저 설정**한다. 게인을 잘못 넣으면 제어기가 duty를 최대까지 올린다
- 팀마다 **비상 차단 담당 1명**을 지정하고, 전원 스위치에 손이 닿는 위치에 서게 한다
- 게인을 바꿀 때는 **작은 값에서 큰 값으로** 올린다. 큰 값에서 시작하지 않는다
- 모터가 진동하거나 소리가 커지면 **즉시 지령을 0으로** 하고 전원을 내린다
- 축·커플링 근처에 손·측정 리드·옷소매를 두지 않는다
- 부하를 손으로 주는 실습은 **회전체를 직접 잡지 않고** 브레이크 패드나 천을 사용한다
- 연속 운전 후 모터 권선과 MOSFET은 뜨겁다. 손으로 확인하지 않는다
